# Loan Support Agent

I completed the **Cred (Banking & FinTech)** track.

This repository is a loan-operations support agent for **Meridian Bank**, a fictional lender.
It answers loan-policy questions from a knowledge base written for this brief, and looks up loan applications from a dataset generated for this brief.

**Everything runs under `MOCK_LLM` with zero API keys and zero network access at inference time.**
Every graded transcript in [`transcripts/`](transcripts/) was produced in that mode.
A real language model can optionally be wired in behind the `LLM_PROVIDER` environment variable, and no acceptance criterion depends on it.

The brief this repository answers is [`reference/problem-statement.md`](reference/problem-statement.md).

## Part 1 Task 1 - dataset design

`dataset.py` generates 100 loan applications from a single seeded `random.Random`, in a fixed field order per record, so the whole list is reproducible from the seed alone.

<!-- Generated by scripts/run_part1.py. Do not edit by hand. -->

| Seed | Records | Fraud flagged | Categories | Statuses |
|---|---|---|---|---|
| `1` | 100 | 16 (16.0%) | 5 | 5 |

<!-- End of generated block. -->

Everything needed to reproduce the dataset, which the brief asks to be stated here:

**Seed: `1`.**
Seeds were scanned in order from 1 and the first one meeting every structural invariant was taken; seed 1 passed, so there was no hunt. That is the weights doing the work rather than the seed. No record was hand-edited.

**Category weights.** Personal 0.34, Auto 0.22, Home 0.20, Education 0.12, Business 0.12.
A retail lending mix, where unsecured personal lending is the highest-volume product by count. At 100 records the least frequent category expects 12, against the brief's floor of 3.

**Status weights.** Under Review 0.24, Approved 0.22, Disbursed 0.22, Submitted 0.18, Rejected 0.14.
A support queue is dominated by in-flight and recently completed applications, so the terminal states are not the largest buckets.

**Amount range.** Sampled log-uniformly inside a per-category band, then rounded to the nearest 1000: `amount = round(exp(uniform(log(lo), log(hi))), -3)`.

| Category | Band (INR) | Basis |
|---|---|---|
| Personal Loan | 50,000 to 40,00,000 | Published Indian personal-loan ranges for 2026. |
| Auto Loan | 1,00,000 to 25,00,000 | SBI states a 1 lakh minimum, HDFC a 25 lakh maximum for a new car. |
| Education Loan | 1,00,000 to 50,00,000 | HDFC lends up to 50 lakh unsecured for premier institutes. |
| Business Loan | 1,00,000 to 50,00,000 | Published MSME ranges run 50,000 to 50 lakh and above. |
| Home Loan | 10,00,000 to 1,50,00,000 | **A modelling choice, not a lender limit.** SBI quotes 50,000 to 50 crore, four orders of magnitude and useless to sample from. |

**Why the range is realistic**, as the brief asks: each band is the published range for that product at a large Indian lender rather than one global range, because a single uniform range produces a Home Loan of 80 thousand rupees beside a Personal Loan of 48 lakh, which no real loan book contains.
Log-uniform rather than uniform because a real loan book is dominated by smaller tickets, and Part 2's escalation threshold is justified as a percentile of this column.

**Days since created.** `int(rng.triangular(0, 30, 8))`, clamped to 0 to 30, skewed toward recent because most items in a live support queue are new.

**Fraud flag.** A category-dependent Bernoulli draw rather than a flat coin toss: base 0.15, plus 0.10 for Business Loan, plus 0.05 for Personal Loan, expected rate about 17.9 percent. Unsecured and business lending carry higher fraud incidence, so the flag carries signal Part 2's escalation score can use.

`data/loan_applications.json` is a committed snapshot, and a test asserts the generator still reproduces it byte for byte by SHA-256.
Full report: [`transcripts/part1-dataset.txt`](transcripts/part1-dataset.txt). Seed scan and persistence rationale: spec section 5.2.

`dataset.py` also feeds a seven-table SQLite store built from the same seed, which adds no field the brief asked for and moves no value it did: [`docs/relational-store.md`](docs/relational-store.md).

## Part 1 Task 2 - the knowledge base

18 plain-text documents in [`knowledge_base/`](knowledge_base/), all written from scratch: **12 required topics**, one per topic the brief names, plus **6 deliberately confusable neighbours**.
Titles and topics live beside them in [`catalogue.json`](knowledge_base/catalogue.json), and `rag/kb.py` refuses to load if the two describe different sets.

Documents run 10 to 15 sentences rather than the brief's 2 to 5, because at 2 to 5 both chunkers produce nearly the same chunks and Task 5 would have nothing to measure.
The six neighbours exist so that an evaluation query can have more than one relevant document; without them both collections score Precision@3 of one third and the recommendation has nothing to cite.

Which neighbour sits beside which required topic, and why each pair is confusable: spec section 6.2.

## Part 1 Task 3 - chunking and indexing

Both strategies are pure functions in [`rag/chunking.py`](rag/chunking.py), indexed into two **separate** ChromaDB collections by [`rag/index.py`](rag/index.py).

| Collection | Strategy | Chunks |
|---|---|---|
| `kb_fixed_400_80` | Fixed-size with overlap, 400 characters, 80 overlap | 89 |
| `kb_sentences` | Sentence-based, regex splitter with an abbreviation guard | 215 |

Embeddings use `all-MiniLM-L6-v2` with `normalize_embeddings=True`, and both collections use `{"hnsw:space": "cosine"}`, so Chroma's distance converts to similarity as exactly `1 - distance`.
Parameters started at 400/80 and finished there; the documents measured 124 characters per sentence against an assumed 134, well inside tolerance. Spec section 7.

## Part 1 Task 4 - grounded generation and the measured threshold

### The threshold was measured, not preset

29 probes were measured against both collections: 12 in-scope, one per required topic, and 17 deliberately out-of-scope, which oversamples the brief's floors of 3 and 2 because the gap between the clusters is the entire justification.

<!-- Generated by scripts/run_part1.py. Do not edit by hand. -->

| Measurement | Value |
|---|---|
| Minimum in-scope top-1 similarity | 0.3263 |
| Maximum out-of-scope top-1 similarity | 0.2870 |
| Gap between the clusters | 0.0393 |
| **Chosen threshold T** | **0.3066** |

<!-- End of generated block. -->

`T` is the midpoint of the two observed clusters, pooled across both collections, because the answer decision has to be a single rule Part 2 imports.
**A tutorial preset of 0.5 would have wrongly refused 8 of the 24 in-scope measurements**: the in-scope cluster runs from 0.33 to 0.76, so 0.5 cuts through the middle of it, and 0.6 and 0.7 are worse.

Every measured value: [`transcripts/part1-calibration.txt`](transcripts/part1-calibration.txt). Derivation: spec section 8.2.

### Scope is decided before retrieval, because similarity cannot decide it

The threshold decides **groundedness** well and **topicality** not at all. Holding one sentence frame fixed and swapping only the product noun, "fixed deposit" scores **0.6805** where "car insurance policy" sits, while the lowest genuine in-scope probe scores **0.3263** against the document that answers it - so an out-of-catalogue question can sit more than twice as high as a real one.

[`rag/scope.py`](rag/scope.py) therefore decides topicality first, by deterministic string matching over the catalogue and thirteen `KNOWN_ADJACENT` phrases, before any vector search. All 10 `outside_boundary` items refuse at the gate on both collections, all 12 `answerable` items still answer, and the near-domain false-answer rate falls from **15 of 24 readings to 3 of 24**.

**The list is curated, which is its weakness, stated in the same breath as the success.** An adjacent product nobody thought to add still falls through to a threshold that cannot catch it. The full account, including four entries that matched topics rather than products and had to be removed, is spec section 18.1 item 8.

### The answer decision

The gate has already run and passed. An answer is then produced only when **both** hold:

1. `top1.similarity >= 0.3066`
2. At least 2 of the top 3 chunks share the same parent `doc_id`

Similarity alone would let a single confident chunk be confidently wrong; the second condition asks the knowledge base to agree with itself before the system speaks.

**Known limitation, recorded rather than hidden.** "What documents are needed for KYC?" scores 0.5124, far above the threshold, but its top three chunks land on three different parents, so the system refuses. That is the price of the six confusable neighbours, and `tests/test_generate.py` pins it as expected behaviour.

### Demonstration

[`transcripts/part1-generation.txt`](transcripts/part1-generation.txt) shows all **12 in-scope queries answered with citations plus 2 deliberately out-of-scope queries triggering the fallback**, for both collections, against a floor of 5 and 1. Under `MOCK_LLM` generation is deterministic template synthesis filled only from sentences in the retrieved chunks, and a test asserts every output sentence is a substring of that context. Spec section 8.4.

## Part 1 Task 5 - comparing the two strategies

Chunks are mapped back to their parent `doc_id` and deduplicated before scoring, as the brief requires.
The 12 queries carry graded gold sets - 4 with one relevant document, 5 with two, 3 with three - and were authored and committed before any retrieval code existed.

<!-- Generated by scripts/run_part1.py. Do not edit by hand. -->

| Collection | Chunks | Mean \|R\| | Precision@3 | Recall@3 |
|---|---|---|---|---|
| `kb_fixed_400_80` | 89 | 1.25 | 0.7917 | 0.5972 |
| `kb_sentences` | 215 | 1.33 | 0.8750 | 0.6528 |

<!-- End of generated block. -->

**Deploy `kb_sentences`, and it becomes Part 2's fixed RAG input.**
It wins on both metrics while carrying the *higher* mean `|R|`, so the precision margin is real retrieval quality rather than the denominator flattering a collection that concentrates. The gap is decided by the multi-document queries: sentence chunks are shorter and more numerous, 215 against 89, letting the top 3 span more parents exactly where the fixed collection collapses onto one document.

Per-query arithmetic for both collections: [`transcripts/part1-evaluation.txt`](transcripts/part1-evaluation.txt).
The denominator asymmetry and why it does not change the answer: spec section 9.2.

## Part 3 - the API, the request log, and the RAG triad

A FastAPI deployment over the Part 2 agent: `POST /ask` (the envelope unchanged, per D-66) and `POST /add-document`, which writes a runtime document into the gitignored `data/uploads/` and indexes it into `kb_sentences` only, never into `knowledge_base/` (D-72). A per-request JSON log line joins to the response's own `trace_id`, and the RAG triad scores fifteen golden-dataset queries on three signals rather than one.

| Part 3 measurement | Value |
|---|---|
| Triad rows scored | 15 |
| Average context relevance | 0.4214 |
| Average groundedness | 0.6695 |

Under `MOCK_LLM` the three scores above are deterministic lexical proxies - n-gram containment between the query, the answer and the retrieved context - rather than a model's judgement (D-74); a real provider is asked the identical three questions through the same prompt.

## The optional Groq provider

`MOCK_LLM` is the default and the mode every graded transcript was produced in. A real model is optional and cannot affect anything graded.

```bash
cp .env.example .env          # then put your key in it; .env is gitignored
LLM_PROVIDER=groq .venv/bin/python scripts/run_groq_demo.py
```

`LLM_PROVIDER`, `GROQ_API_KEY`, `GROQ_MODEL` and `LOG_LEVEL` are named in [`.env.example`](.env.example) with no values.

Three properties make the switch safe: **both graded runners exit non-zero under a real provider**, **the test suite is pinned to `mock`** whatever `.env` says, and **nothing degrades quietly** - a missing key, an HTTP error or a truncated completion all raise rather than being passed off as the knowledge base declining to answer.
Only the answer sentence changes when the key is set; the gate, the router, retrieval and the guardrails stay deterministic. Spec section 20.

## Observability

Every boundary emits one JSON line, keyed on the same deterministic `trace_id` the response envelope carries.

```bash
LOG_LEVEL=INFO .venv/bin/python -m pytest tests/test_generate.py -q
```

Lines go to stderr and a gitignored `logs/`, never into `transcripts/` or the tables above, because a log line carries a clock and those bytes are guaranteed.
Queries pass through the masker the guardrails use, the API key is never logged, and context is logged as document ids and counts rather than text. Spec section 21.

## Tests

**372 tests, all passing offline.** 222 are Part 1's, 139 Part 2's, and 11 cover the provider and the logging spine.
Each acceptance criterion in the brief has a test that restates it; the full mapping is spec section 16.

**Precision@3 and Recall@3 are deliberately not pinned by any test.** They move legitimately when chunk parameters are tuned, so a test that pinned them would fight the work and get deleted.
